# Heading rename/move identity persisted via a git-synced redirect log

When a heading is renamed or moved ([ADR-0002](0002-linking-granularity-fixed-at-heading-level-for-mvp.md), [ADR-0005](0005-page-per-file-with-frontmatter-id-and-slug-addressed-headings.md)), a link addressing it by its old slug needs to keep resolving until every file that references it can be updated. The obvious approach — a redirect table living only in the in-memory [derived index](../../CONTEXT.md) — turns out to be unsound: the derived index is rebuilt from the markdown files alone and is never git-synced, so a redirect created on one device vanishes the moment the app restarts or another device pulls the rename, before the background cleanup job (which rewrites referencing files to the new heading directly) has had a chance to run. The link then breaks silently, with no trace left of the rename that caused it. A prototype (`.scratch/cerebrite-mvp/issues/04-stable-heading-identity.prototype.html`) confirmed the redirect-plus-cleanup-job mechanism itself works — it disambiguates slug collisions and collapses multi-hop rename chains correctly — but only once the redirect entries are made durable enough to outlive a single session.

The redirect table is therefore kept in its own small, git-synced, plaintext file, separate from the rest of the derived index, one entry per line so concurrent renames on different devices merge as ordinary line additions. This file carries no linkable content, so it isn't page content subject to clean markdown ([ADR-0003](0003-clean-markdown-excludes-round-trip-fidelity.md)) — it's the one deliberate exception to "the derived index is never git-synced." An entry is pruned once the cleanup job has rewritten every file that referenced the old heading identity; "temporary" describes that lifecycle, not an absence of persistence. Renaming the same heading on two devices before either syncs is still a genuine conflict, left to ordinary git conflict handling ([ADR-0006](0006-automatic-git-sync-with-conflict-detection-and-copy-safety-net.md)) rather than solved here.

The exact file format, location, and pruning trigger were resolved in [05-redirect-log-format](../../.scratch/cerebrite-mvp/issues/05-redirect-log-format.md): `.cerebrite/redirects.tsv`, tab-separated `oldPageId#oldSlug\tnewPageId#newSlug\ttimestamp\tdeviceId` lines keyed by frontmatter page id, **inserted in sorted-by-key order rather than blindly appended at end-of-file**. That research corrected this ADR's original assumption above — verified directly against real `git merge`, blind end-of-file append produces git's well-known "changelog conflict" false-positive between two entirely unrelated concurrent renames, because two insertions anchored at the same position conflict regardless of content relatedness. Sorted-by-key insertion fixes the common case while still correctly conflicting when the same heading is renamed differently on two devices; a narrower residual false-positive (sort-adjacent or empty-log collisions) remains, is always safe (never silent data loss), and is accepted rather than solved with a bespoke merge driver, per this ADR's and [ADR-0006](0006-automatic-git-sync-with-conflict-detection-and-copy-safety-net.md)'s shared "no bespoke merge logic" boundary.
