# Tech Stack & Core Architecture — Research (2026-08-21)

## Recommendation (summary)

**One stack, all three platforms:**

- **UI framework: Tauri 2.x**, with a single web-based frontend (TypeScript, any framework — React/Svelte/vanilla) shared across Windows, Linux, *and* Android. Tauri's Rust backend doubles as the shared core, so this is not "framework vs. shared-core" as separate choices — Tauri's architecture *is* a shared Rust core with a thin webview shell per platform.
- **WYSIWYG editor: Milkdown** (ProseMirror + remark) embedded in the webview for Windows/Linux. On Android, render the *same webview UI* but swap in a plain `<textarea>`/CodeMirror 6 plaintext surface — no native editor component needed since Android is plaintext-only for MVP.
- **Search: SQLite FTS5** via `rusqlite`, compiled once into the shared Rust core.
- **Derived-index storage: a single on-disk SQLite database** (the same file backs both FTS5 search and a plain backlinks table), rebuilt from markdown on launch and after every completed git sync — **no file-system watcher** for MVP.

Runner-up considered seriously: Kotlin Multiplatform + Compose Multiplatform with a Rust core reached over UniFFI/JNI. It is a credible, fully-maintained alternative (see §1) but adds a second language boundary (Rust↔Kotlin) and a second UI toolkit to test on desktop, for no clear benefit over Tauri given the WYSIWYG requirement is desktop-only and Android is plaintext-only. If native Android/desktop look-and-feel becomes a hard requirement later, Compose Multiplatform is the fallback, not Flutter or .NET MAUI (both eliminated below).

### Why Tauri over Compose Multiplatform

Both pass the maintenance filter. The deciding factors:

1. **The WYSIWYG requirement is desktop-only; Android is plaintext-only.** This is exactly the shape Tauri is built for: ship a rich web-based editor (ProseMirror-class) on desktop, and the *same* webview UI degrades gracefully to a plain textarea on Android — one frontend codebase, no native rewrite for the lesser Android surface. Compose Multiplatform would require either (a) a genuinely different, simpler Android editor composable plus a separate desktop rich-editor composable (two UIs to maintain), or (b) forcing Compose's rich-text ecosystem (still pre-1.0, see below) onto desktop where a much more mature web-based WYSIWYG ecosystem already exists.
2. **Editor ecosystem maturity.** The web-based ProseMirror ecosystem (Milkdown, Tiptap) is a decade-mature, heavily-used WYSIWYG foundation (see §1b). Compose Multiplatform's rich-text-editor story (`compose-rich-editor`, `hyphen`, `compose-markdown-editor`) is real but young — `compose-rich-editor`'s own releases are still tagged `1.0.0-rc14` as of 2026 ([releases](https://github.com/MohamedRejeb/Compose-Rich-Editor/releases)), i.e. pre-1.0.
3. **Rust core is a stronger fit for the file-first, git-native domain.** Cerebrite's actual hard problems — parsing markdown/frontmatter, walking ~500 files, maintaining a backlink index, driving `git` — are naturally Rust-shaped (fast, single static binary, no GC pauses, no JVM startup tax on Android). Tauri's architecture makes this the *primary* language, with the webview as a thin, disposable shell — closer to the "shared core + native-ish shell" pattern the research question asks to compare, except the "shell" is one webview instead of three native UIs, which is strictly less work. Compose Multiplatform would instead make Kotlin primary and push a Rust core (if you kept one, e.g. for `tantivy`) behind a UniFFI/JNI boundary purely for search — extra glue for no benefit, since SQLite FTS5 via a well-supported JVM/Android SQLite path is available natively in Kotlin/Android anyway.
4. **No separate "native UI per platform" tier is needed.** The prompt's second architectural pattern (shared core + separate native UIs) mainly buys native look-and-feel and native performance. For a text-heavy note-taking app this is a "nice to have," not a differentiator big enough to justify three UI codebases (WinUI/native GTK, Compose for Android, etc.) versus one Tauri webview UI. If native polish becomes a business requirement post-MVP, Compose Multiplatform is the documented fallback — not a rewrite from scratch, since the Rust core's design (plain functions/CLI-shaped API) would still port to a UniFFI boundary.

**Effect of the "no round-trip fidelity" decision:** this is what makes Milkdown/Tiptap viable at all — both are ProseMirror-based, which means they always own the document as a ProseMirror doc-tree and *serialize* markdown out; they do not diff-patch the original text to preserve exact formatting. Since Cerebrite's "clean markdown" bar is explicitly "no injected bookkeeping metadata," not "byte-identical on save," a ProseMirror-based editor is fully acceptable — this bar would be a much harder (arguably disqualifying) constraint for these tools if strict round-trip fidelity were required, since ProseMirror-based editors are well known for reflowing/renormalizing markdown on serialize.

### Throughput reasoning for the ~500-file, sub-second target

- A real-world Android FTS5 benchmark (secondary source, [dzolnai.medium.com](https://dzolnai.medium.com/speed-up-searching-in-your-app-by-using-sqlite-and-fts-8896ab74b598)) reports building a full FTS5 index over **4,380 records in ~2.1 seconds on a Pixel 8 Pro**, and ~28 seconds on a 2014-era Samsung Tab S — i.e. even on genuinely old/low-end Android hardware, indexing thousands of short text records lands in the tens-of-seconds range, and on any device from the last ~5 years it's low single-digit seconds for ~10x our target corpus (500 files vs. 4,380 records).
- Separately, FTS5 is reported as ~78x faster than a pure-Python engine (Whoosh) for indexing 5,000 short documents ([dev.to benchmark](https://dev.to/priyasundaram/sqlite-fts5-is-faster-than-whoosh-so-why-would-you-ever-use-a-pure-python-search-engine-3o6g)) — directionally useful but not a primary-source number.
- **Reasoned estimate for Cerebrite:** ~500 markdown notes (each realistically a few hundred words to a few KB) is a smaller corpus, by document count, than the 4,380-record Android benchmark above, and our documents being longer per-file doesn't change the order of magnitude — FTS5 indexing throughput is dominated by tokenization + B-tree insert cost per token, and a full personal KB of ~500 files is well under a megabyte of tokenizable text in the typical case. This comfortably clears "sub-second," including on Android hardware, with headroom to spare (the benchmark corpus is ~9x larger by row count and still only took ~2s on a mid-tier 2023 phone).
- **Flag:** no benchmark found is an exact match for "500 markdown files of realistic note length" — the estimate above is reasoned from adjacent primary/secondary data, not a direct measurement. Recommend a throwaway prototype (index the actual eventual test corpus, or a synthetic 500-file corpus, with `rusqlite`+FTS5 cross-compiled to an Android emulator) before locking this in, per the Risks section.

## 3. Derived-index storage and rebuild trigger

### Storage: SQLite file, not pure in-memory

**Recommendation: a single on-disk SQLite database** (not exported to git — this is the "derived index," disposable and rebuildable) holding:
- an FTS5 virtual table for full-text search, and
- a plain `links(source_id, source_heading, target_id, target_heading)` table for backlinks — a simple indexed lookup table, not a graph database, matching the MVP's "backlinks only" scope.

Reasoning:
- **Cold-start cost is not a real tradeoff at this N.** Given §2's throughput evidence, a full from-scratch rebuild of ~500 files is sub-second even on Android. This means the disk-backed cache is not there to avoid a slow rebuild — a from-memory rebuild-on-launch would also be fast enough. The disk cache earns its place for a different reason: **it makes "rebuild" cheap enough to call liberally** (on every launch and after every git sync) without users perceiving a delay, and it gives us a durable place to do incremental updates later (SQLite `INSERT OR REPLACE` per changed file, keyed by file mtime/hash) rather than always doing a full walk — an optimization path that's simply unavailable to a pure in-memory design that discards state on exit.
- **Sync-safety:** because git pulls happen in the background and can change files outside the app's own edit path, the source of truth (files) can drift out of sync with any cached index at arbitrary times. Since a full rebuild is cheap (sub-second) at this scale, the simplest correct policy is: **treat the SQLite cache as fully disposable and always rebuild-or-reconcile it after any event that could have changed files on disk** (see trigger discussion below), rather than trying to build fine-grained incremental invalidation logic for MVP. This sidesteps most of the "keeping a disk cache in sync with externally-modified files" complexity the prompt asks about — the answer is "don't try to keep it in sync incrementally yet; it's cheap enough to just redo the relevant work."
- **Concurrency/locking:** SQLite's file locking is well-understood and battle-tested on Windows, Linux, and Android (Android's own `SQLiteOpenHelper`/Room stack is built directly on it) — using WAL mode avoids reader/writer contention between a background rebuild and a foreground search query, which is the only concurrency scenario Cerebrite has (single process, single user, no multi-process access to this file). This is a non-issue compared to, e.g., coordinating writes to the *markdown files themselves*, which is a separate, already-settled concern (git sync).

### Rebuild trigger: sync-completion + launch, not a persistent file watcher

**Recommendation: rebuild (or reconcile) the derived index on app launch, and again whenever a background git sync completes (pull with incoming changes).** Do **not** build a persistent cross-platform file-system watcher for MVP.

Reasoning:
- On **desktop** (Windows/Linux), a file watcher is technically easy and reliable: the `notify` crate (Rust) wraps `ReadDirectoryChangesW` (Windows) and `inotify` (Linux) and is actively maintained — newest published version `9.0.0-rc.4`/stable `8.2.0`, last crates.io update **May 2, 2026** ([crates.io API](https://crates.io/api/v1/crates/notify)) — and is used by tools like `rust-analyzer`, `mdBook`, and **Zed** ([notify-rs repo](https://github.com/notify-rs/notify)). So "is it practical" is not in question for desktop.
- On **Android**, this app's own design removes most of the motivation for a watcher: git sync is already the *only* channel through which files change outside a direct in-app edit (there's no separate "another program edits your notes folder" scenario on a phone the way there might be on desktop). So the two triggers that matter — "user edited a note in-app" (already known, no watcher needed) and "a background git sync just pulled changes" (an event the app's own sync code already knows about, since it initiated the pull) — are both already observable without any OS-level file watching. A watcher would only add value for the case of *another process on the same device* editing the notes folder concurrently, which isn't a real scenario for this app.
- Android's own background-execution model makes a persistent watcher actively risky rather than merely unnecessary: Android restricts long-running background work outside of foreground services/WorkManager, and services are curtailed by Doze/App Standby when the screen is off and the device is idle ([Android Developers: Background Execution Limits](https://developer.android.com/about/versions/oreo/background), [Background work restrictions](https://developer.android.com/develop/background-work/background-tasks/bg-work-restrictions)). A `FileObserver`-based watcher would need to run continuously to catch changes made while the app is backgrounded — exactly the pattern these restrictions target. Tying the rebuild to "sync just completed" instead means the rebuild happens on an event the app is already awake for (it's mid-sync), no separate watcher/service needed, and no fight with Doze.
- **Net effect:** "rebuild-on-launch + rebuild-after-sync" is not a compromise forced by Android's constraints — it is the objectively simpler design on *all three* platforms given this app's specific sync model, and it happens to also be the one that avoids Android's background-execution pitfalls entirely. A file watcher would only be worth adding later if desktop users want near-live backlink updates while another tool is editing the same repo, which is a real but non-MVP scenario.

## Risks / open questions

1. **No benchmark found for the exact shape of Cerebrite's real corpus** (500 markdown files, realistic note length/structure, including heading-level parsing for backlinks) on **actual low/mid-range Android hardware**. The reasoning in §2 is grounded in adjacent primary/secondary data (Android FTS5 benchmark on a different corpus shape), not a direct measurement. **Recommend a throwaway prototype**: cross-compile `rusqlite`+FTS5 to Android, generate a synthetic ~500-file corpus resembling real notes, and measure cold rebuild time on a low/mid-tier physical device (not just an emulator) before locking in the "always full rebuild" policy.
2. **Tantivy's post-Datadog-acquisition trajectory** is a secondary-source claim (Quickwit's own blog says they'll keep maintaining it and relicense to Apache 2.0) — moot for the recommended stack since Tantivy wasn't chosen, but worth re-checking if a future search-feature upgrade path leads back to Tantivy.
3. **Tauri Android production maturity beyond "it builds and ships"** — official docs confirm mobile targets and Play Store distribution tooling exist ([Tauri distribute docs](https://v2.tauri.app/distribute/)), and Tauri is used in production by several desktop-first projects (Spacedrive, AppFlowy, Clash Verge), but I could not find an official Tauri-published list of production Android apps, and one practitioner retrospective blog (2025, secondary source, could not be fetched directly due to a 403) suggested mobile has more rough edges than desktop. **Recommend validating early** with a minimal Tauri Android build (webview + a Rust command round-trip) on a real device before committing significant UI work, specifically checking: WebView version fragmentation across Android OEMs/versions, and cold-start time of the bundled Rust binary on low-end hardware.
4. **Milkdown/Tiptap inside a mobile-context WebView is untested by this research** — Android's requirement is plaintext-only for MVP, so this risk is currently moot, but if WYSIWYG is ever extended to Android, touch/IME interaction with ProseMirror-based editors inside an Android WebView (as opposed to a desktop browser engine) should be explicitly prototyped; this is a known soft spot for ProseMirror-family editors on mobile web generally (not verified against a primary source here).
5. **`git2-rs`** (the natural Rust choice for driving git operations from the core) is actively maintained under the `rust-lang` GitHub org and bundles its own libgit2 source (no external libgit2 install required) — confirmed via its repo, but Android/iOS cross-compilation specifics for `libgit2-sys` were not independently verified against a primary source in this pass and should be smoke-tested alongside item 3.
6. **Flutter and Compose Multiplatform were evaluated as whole-framework alternatives, not fully prototyped** — if Tauri's Android story turns out weaker than the docs suggest (see risk 3), Compose Multiplatform (with a Rust core behind UniFFI, or dropping Rust search entirely in favor of Room/FTS5 or Lucene-on-Android) is the documented fallback, not Flutter or MAUI, which are ruled out above on the Linux-desktop and rich-editor-ecosystem grounds respectively.
